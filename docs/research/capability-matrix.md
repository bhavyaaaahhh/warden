# Capability matrix: offline evaluation of multi-turn, tool-using LLM apps and agents

**Framed question.** What is the best known approach to offline evaluation of LLM apps and agents, especially multi-turn conversations and tool use? That covers the test-case model, how conversations are executed or simulated, scorers and judges, and regression comparison between runs.

**How this was built.** Every cell comes from the nine deep-dive dossiers in `projects/`, and each is pinned to a commit SHA listed in that dossier's header. No new web research was done. Where a dossier is silent, the cell says **Unknown**. I did not fill those cells from memory.

**Legend**
- **Yes** means a first-class, working feature. **Partial** means it exists but is limited, buggy, convention-only, or single-turn only. **No** means the dossier looked and found none. **Unknown** means the dossier doesn't cover it.
- Evidence tags: a cell is **[code]** unless it is marked **[doc]** (docs only, usually closed server behavior) or **[inferred]**.
- `§` links to the dossier section that holds the evidence.
- Column abbreviations:
  - **IA**: Inspect AI
  - **DE**: DeepEval
  - **PF**: promptfoo
  - **TB**: tau-bench (τ1) and tau2-bench (τ2)
  - **LS**: LangSmith SDK + openevals + agentevals
  - **BT**: Braintrust SDKs + autoevals
  - **RG**: Ragas
  - **SC**: LangWatch Scenario
  - **SE**: Strands Evals

## Contradictions and discrepancies found while building the matrix

1. **Ecosystem map [doc] vs dossier [code], Inspect AI multi-turn.** The map says "Yes: README cites multi-turn dialog". The code has no user simulator. Multi-turn means message prefixes and agent loops (`inspect-ai.md` §Multi-turn). Code wins, so the matrix says Partial and No.
2. **Ecosystem map vs dossier, promptfoo simulated user.** The docs present it as a local tau-bench-style provider. The code always POSTs to promptfoo's hosted service, and `userProvider` is never read (`promptfoo.md` §Multi-turn support).
3. **Ecosystem map vs dossier, Braintrust multi-turn.** The map says "Partial". The dossier finds no conversation-typed case and no simulator, only a docs convention, so the matrix says No.
4. **pass^k conventions disagree across projects.** τ1 uses a global n. τ2 drops infra-error trials and uses per-task surviving n. The τ2 leaderboard counts infra errors as failures (#497). Inspect's `pass_k` returns NaN when fewer than k scored epochs remain. The formula is the same, but missing-trial handling differs, so these numbers are not comparable.
5. **agentevals vs openevals trajectory matchers diverge** on a missing-on-both-sides key: one treats it as a match, the other as a mismatch (`langsmith-openevals.md` §Trajectory match).
6. **Strands dossier overstatement.** It says Strands differs from "every other project" by not owning the conversation loop. The Inspect dossier also leaves the user-turn loop to user code. The claim holds against DeepEval, τ-bench, Scenario and openevals.
7. **Scenario dossier's "simulate first, score afterwards" description of promptfoo** is only partly right. promptfoo's red-team Crescendo runs a refusal judge and a grader on every turn (`promptfoo.md` §Multi-turn support, point 3).
8. **Conversation-relevance window.** promptfoo's port of DeepEval's metric defaults to a window of 5 (`promptfoo.md`). DeepEval's `TurnRelevancyMetric` defaults to 10 (`deepeval.md`). These are ports that have drifted apart, not a doc error.
9. **Braintrust base-selection docs are internally inconsistent**: "closest ancestor on main", "most recent on same branch" and "most recent in project" all appear (`braintrust.md` §Open questions).
