Research focus: offline evaluation of LLM apps and agents, especially multi-turn tool-use evaluation.

## Purpose
A config-driven (YAML) CLI and library for **offline** evaluation. It runs a matrix of prompts × providers × test cases, scores each cell with a list of "assertions", stores results in local SQLite, and shows them in a local web viewer that can compare evals side by side. A large part of the codebase is red-teaming: generated adversarial test cases and multi-turn attack "providers". The intended users are app developers and security teams running evals locally or in CI. There is no production-traffic sampling path. OTLP tracing is used only to capture spans from the system under test during an eval, so assertions can inspect them.

## Core abstractions

**Unit of data: test case** — `TestCaseSchema` in `src/types/index.ts` ([L906-L978](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L906-L978))
```ts
TestCaseSchema = z.object({
  description, vars: VarsSchema, provider, providers: string[], prompts: string[],
  providerOutput,            // skip the call and grade a canned output
  assert: (AssertionSet | Assertion)[],
  assertScoringFunction,     // file://…js|py custom aggregator
  options: {...PromptConfig, ...OutputConfig, ...GradingConfig,
             disableConversationVar, runSerially, repeat, ...}.catchall(z.any()),
  threshold, metadata })
```
Trade-off: a test case is only a bag of template `vars` and assertions. It has no first-class "input", "expected output" or "turns" field. Any multi-turn structure has to be encoded in vars (`_conversation`, `initialMessages`, `metadata.conversationId`) or pushed into a provider.

**Batch: test suite / eval** — `TestSuiteSchema` ([L1146-L1230](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L1146-L1230)) holds `providers[]`, `prompts[]`, `tests[]`, `scenarios[]`, `defaultTest`, `derivedMetrics`, `extensions` (hook files) and `tracing`. The matrix is expanded in `src/evaluator.ts:appendRunEvalOptionsForTestCase` ([L2628-L2693](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2628-L2693)). The loop order is repeat → var combinations (the cartesian product of array-valued vars, via `generateVarCombinations`) → provider → prompt (`appendRunEvalOptionsForProvider`, [L2793-L2819](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2793-L2819)). **Each repeat and each var combination gets a new `testIdx`** ([L2668-L2689](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2668-L2689)). A row is identified only by position (`testIdx`, `promptIdx`), with no stable content ID.

**Unit of scoring: assertion** — `AssertionSchema` ([L753-L787](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L753-L787)) has these fields: `type, value, config, threshold, weight, provider (judge), rubricPrompt, metric (named score), transform, contextTransform`. `AssertionSetSchema` ([L734-L749](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L734-L749)) nests a group of assertions with its own weight and threshold.
- The type registry is a closed Zod enum, `BaseAssertionTypesSchema` ([L639-L706](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L639-L706)), with 67 base types. It is extended in two ways: a `not-` prefix derived automatically for every base type ([L721-L731](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L721-L731)), and the special types `select-best | human | max-score`.
- Dispatch goes through a static map, `ASSERTION_HANDLERS: Record<BaseAssertionTypes, (AssertionParams) => GradingResult>` in `src/assertions/index.ts` ([L228-L315](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/index.ts#L228-L315)). Red-team graders are handled separately by the `promptfoo:redteam:*` prefix ([L651-L654](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/index.ts#L651-L654)).
- Trade-off: adding a built-in type means editing the enum and the map. Users extend through `javascript` / `python` / `ruby` / `webhook` assertions, not through a registry.

**Score record: GradingResult** ([L510-L570](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L510-L570)) holds `pass, score, reason, namedScores, namedScoreWeights, tokensUsed, componentResults[], assertion, metadata{graderError?…}`. It is recursive: a test-level result nests one result per assertion.

**Execution record: EvaluateResult** ([L396-L426](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L396-L426)) holds `promptIdx, testIdx, testCase, provider, response, error, failureReason, success, score, latencyMs, gradingResult, namedScores, cost, tokenUsage, traceId`. `ResultFailureReason` ([L380-L387](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/types/index.ts#L380-L387)) is `NONE=0 | ASSERT=1 | ERROR=2`. This separates "the model's answer failed an assertion" from "the run broke", which matters for regression gating.

**Provider** — the system under test and every judge are the same `ApiProvider` interface (`callApi(prompt, context, options)`). Multi-turn drivers (simulated user, red-team strategies) are also providers that wrap the real target, which they receive as `context.originalProvider` (`src/evaluator.ts:callActiveProvider`, [L1067-L1084](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L1067-L1084)). Trade-off: this makes composition very flexible, but a whole conversation collapses into a single provider call that returns a single `output`.

### Multi-turn support

Multi-turn works in three separate ways:

1. **`_conversation` var (scripted, sequential tests).** `attachConversationVar` ([L785-L806](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L785-L806)) injects `vars._conversation = conversations[conversationKey]`. The value is filled by `updateConversationHistory` ([L1168-L1193](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L1168-L1193)) as `{prompt, input, output, metadata}` after each call. The key is `JSON.stringify([providerId, prompt.id, promptIndex, test.metadata.conversationId])` ([L715-L720](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L715-L720)). So each *test case is one turn*, and the ordering of tests in the file is what defines the conversation. Detection is a template-AST check for whether the prompt references `_conversation` (`promptUsesConversationVariable`, [L151-L165](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L151-L165)). If any prompt uses it, **concurrency for the whole eval is forced to 1** (`adjustConcurrencyForSerialFeatures`, [L2986-L3019](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2986-L3019); open since 2024, [issue #385](https://github.com/promptfoo/promptfoo/issues/385)). The history only records outputs, so tool calls and tool results are not replayed as turns.

2. **Simulated user (`promptfoo:simulated-user`)** — `SimulatedUser` in `src/providers/simulatedUser.ts` ([L58-L436](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/providers/simulatedUser.ts#L58-L436)). Config options are `instructions` (templated persona/goal), `maxTurns` (default 10), `stateful`, and `initialMessages` (array or `file://`). The loop is in [L354-L402](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/providers/simulatedUser.ts#L354-L402):
   - It flips roles and asks the user model for the next message.
   - It stops if that message contains the literal string `###STOP###`.
   - Otherwise it sends either `[system(prompt), ...messages]` or, when stateful, only the last user message plus `sessionId` to the target.
   - It fails the whole conversation on the first error.

   The output is the transcript flattened to `"User: …\n---\nAssistant: …"`, with `metadata.messages` attached ([L416-L435](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/providers/simulatedUser.ts#L416-L435)). **The user model is always promptfoo's hosted service.** `PromptfooSimulatedUserProvider.callApi` POSTs `{task:'tau', instructions, history}` to `getRemoteGenerationUrl()` ([src/providers/promptfoo.ts L321-L393](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/providers/promptfoo.ts#L321-L393)), and returns an error if remote generation is disabled. The declared `config.userProvider` option ([L38](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/providers/simulatedUser.ts#L38)) is never read. Assertions grade only the final transcript string, never individual turns.

3. **Red-team multi-turn strategies.** A strategy rewrites each test case so that its `provider` becomes an attack provider wrapping the target. For example, `addCrescendo` sets `provider.id='promptfoo:redteam:crescendo'` and suffixes metrics with `/Crescendo` (`src/redteam/strategies/crescendo.ts`).
   - **Crescendo** (`src/redteam/providers/crescendo/index.ts:CrescendoProvider`, [L182-L231](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/crescendo/index.ts#L182-L231)) keeps a `MemorySystem` of conversations, with `maxTurns` and `maxBacktracks`. On every turn a refusal judge runs. If the target refused and the provider is not stateful, it **backtracks**: it rewinds the target conversation in memory, feeds the refusal rationale back to the attacker, and does not count the round ([L602-L642](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/crescendo/index.ts#L602-L642)). Otherwise it runs the plugin grader with `conversationHistory` and `redteamHistory` in the grading context ([L644-L724](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/crescendo/index.ts#L644-L724)). `maxTurns` is capped at 10 for users not logged in ([L209-L212](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/crescendo/index.ts#L209-L212)).
   - **GOAT** (`src/redteam/providers/goat.ts:GoatProvider`, [L142](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/goat.ts#L142)) runs a turn loop at [L287](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/goat.ts#L287). The attacker is *only* remote: it POSTs `{task:'goat', goal, messages, failureReason, traceSummary}` to the promptfoo API ([L407-L437](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/goat.ts#L407-L437)).
   - **Iterative (PAIR-style)** (`src/redteam/providers/iterative.ts`) is not a conversation. It makes `numIterations` independent single-turn refinements ([L259](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/iterative.ts#L259)), each scored by a JSON judge that compares `currentResponse.rating` with `previousBestResponse.rating` ([L709-L790](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/redteam/providers/iterative.ts#L709-L790)).
   - Hydra, Goblin, mischievous-user (a subclass of SimulatedUser) and others live in `src/redteam/providers/`. They were not examined.

## Assertion implementations

- **Deterministic.** These are simple handlers (`contains*`, `regex`, `equals`, `is-json`, `levenshtein`, `rouge-n`, `bleu`, `latency`, `cost`, …), one file each under `src/assertions/`. `not-` inversion is passed in as `inverse`.
- **Weights and thresholds.** `AssertionsResult.addResult` / `testResult` in `src/assertions/assertionsResult.ts` ([L261-L422](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/assertionsResult.ts#L261-L422)):
  - The score is `Σ score·weight / Σ weight`.
  - Without a threshold, the test passes only if *every* assertion passed.
  - With a numeric `threshold`, pass becomes `score >= threshold`. This **overrides** individual failures, and the code deliberately honors 0, null and NaN edge cases ([L332-L342](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/assertionsResult.ts#L332-L342)).
  - `weight: 0` means the assertion can never fail and only contributes a metric (`src/assertions/index.ts` [L671-L677](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/index.ts#L671-L677)).
  - Named metrics are weighted averages kept per `metric` name.
  - A custom `assertScoringFunction(namedScores, {componentResults,…})` can replace the result. If it throws, the test fails with score 0.
  - A red-team guardrail block forces pass.
- **llm-rubric.** `matchesLlmRubric` (`src/matchers/llmGrading.ts` L181) calls `runJsonGradingPrompt` (`src/matchers/rubric.ts` [L843-L918](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/matchers/rubric.ts#L843-L918)). The prompt is `DEFAULT_GRADING_PROMPT` (`src/prompts/grading.ts` L11): a system message with two few-shot examples, asking for `{reason, pass, score}`. It can be overridden with `rubricPrompt`, including `file://`. Parsing takes the first JSON object via `extractJsonObjects`. `pass` defaults to `true` if missing and string values are coerced (`/^(true|yes|pass|y)$/`). `score` falls back to `Number(pass)`. When a threshold is set, `pass = pass && score >= threshold`. Red-team configs may send the call to promptfoo's remote grader instead.
- **model-graded-closedqa / factuality.** `matchesClosedQa` (L382) uses the OpenAI-evals closedqa prompt (`OPENAI_CLOSED_QA_PROMPT`). `matchesFactuality` (L323) uses `PROMPTFOO_FACTUALITY_PROMPT`, a letter-category (A–E) classification. Both are in `src/matchers/llmGrading.ts`.
- **g-eval.** `matchesGEval` ([L454-L612](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/matchers/llmGrading.ts#L454-L612)) makes two calls. The first generates evaluation steps from the criteria and regex-extracts `{"steps"…}`. The second produces an integer score from 0 to 10. The result is `score = raw/10` and `pass = score >= threshold`. Out-of-range or missing scores are hard failures. There is **no probability-weighted scoring** (the G-Eval paper uses token logprobs).
- **select-best (pairwise/N-way).** `matchesSelectBest` (`src/matchers/comparison.ts` L16) uses `SELECT_BEST_PROMPT`, which lists the outputs by index and asks for a single integer. The first integer found in the reply is parsed. The winner gets pass/1 and all others get fail/0, so every non-winning output **fails** the test. The assertion runs *after* all rows for the same `testIdx` are complete (`Evaluator.processSelectBestAssertionForTest`, `src/evaluator.ts` [L4256-L4335](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L4256-L4335)). There is no position swapping, which leaves position bias unmitigated. `max-score` (`selectMaxScore`, L102) is a deterministic alternative: it picks the argmax of other assertions' weighted scores.
- **agent-rubric.** `matchesAgentRubric` (`src/matchers/agent.ts`) is llm-rubric run by an *agentic* judge (Codex SDK, Claude Agent SDK, opencode…) that can use tools to gather evidence.
- **conversation-relevance.** A port of DeepEval's metric (`src/external/assertions/deepeval.ts` [L19-L60](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/external/assertions/deepeval.ts#L19-L60)). It slides a window (default 5) over `vars._conversation` and reports the fraction of relevant windows against a threshold (default 0.5). It is the only built-in assertion that reads `_conversation`.
- **Grader-error semantics.** `graderFail` tags transport and parse failures with `metadata.graderError` (`src/matchers/shared.ts` [L53-L61](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/matchers/shared.ts#L53-L61)). This stops `not-llm-rubric` / `not-g-eval` from flipping a judge error into a pass. However, a grader error still ends up as `failureReason=ASSERT` with score 0 rather than `ERROR`. That is inferred from `applyGradingResult` ([L608-L623](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L608-L623)); only thrown exceptions become ERROR.

## Tool-call and trajectory assertions

- **`is-valid-openai-tools-call`** (`src/assertions/openai.ts` [L7-L110](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/openai.ts#L7-L110)) takes `output.tool_calls`. For each call it runs `validateFunctionCall`, which parses `arguments` JSON and checks it with **AJV against the provider's configured `tools` schema** (`src/providers/openai/util.ts` L1290-L1326). It reads the tools from the provider config (`(provider as OpenAiChatCompletionProvider).config.tools`), so it is tied to OpenAI's format and to the SUT's config. MCP results are detected by string-matching `"MCP Tool Result"`.
- **`tool-call-f1`** (`src/assertions/toolCallF1.ts` [L370-L433](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/toolCallF1.ts#L370-L433)) computes set-based precision, recall and F1 over tool *names* only. It ignores order, count and arguments, and the default threshold is 1.0. `extractToolNames` (L216-L347) normalizes OpenAI chat, OpenAI Responses, Anthropic `tool_use`, Gemini `functionCall` and Live formats. It also recovers JSON blocks from mixed text with a linear-time scanner that has hard work limits (L20-L201).
- **`trajectory:*` (trace-based)** — `src/assertions/trajectory.ts`. These read **OTel spans** from the local trace store (`params.assertionValueContext.trace`), not the model output. `extractTrajectorySteps` (`trajectoryUtils.ts` L315) normalizes spans into `{type: tool|command|search|message|reasoning|span, name, args, statusCode…}`. It uses attribute families such as `tool.name`, `gen_ai.tool.*`, `ai.toolCall.*` and `codex.mcp.*` (`src/tracing/toolAttributes.ts` L22-L56).
  - `trajectory:tool-used`: name or glob list, or `{min,max}` counts ([L136-L219](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/trajectory.ts#L136-L219)).
  - `trajectory:tool-sequence`: `exact` or `in_order` subsequence ([L431-L500](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/trajectory.ts#L431-L500)).
  - `trajectory:tool-args-match`: `partial` or `exact` deep-equal, with `ignore` globs and `defaults` stripping. It passes if *any* matching call matches, and is hardened against `__proto__` injection ([L502-L558](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/trajectory.ts#L502-L558)).
  - `trajectory:step-count` ([L579-L633](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/trajectory.ts#L579-L633)).
  - `trajectory:goal-success`: an LLM judge over `summarizeTrajectoryForJudge` (head 12 and tail 12 steps, with the middle collapsed) plus the final output ([L635-L668](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/trajectory.ts#L635-L668)).
  - None of these checks step success or failure yet: [issue #10607](https://github.com/promptfoo/promptfoo/issues/10607), open. They require the SUT to emit OTel spans with the right attributes, and one provider (opencode) is known not to propagate `traceparent` ([#10518](https://github.com/promptfoo/promptfoo/issues/10518)).
- **Also present:** `trace-span-count`, `trace-span-duration`, `trace-error-spans` and `skill-used`. These were not examined.

## Execution model

- **Two-level concurrency.** Eval steps (one prompt × provider × test × repeat cell) run through `async.forEachOfLimit(concurrentRunEvalOptions, concurrency)` (`Evaluator.runConcurrentEvalSteps`, `src/evaluator.ts` [L4080-L4111](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L4080-L4111)). Steps with `options.runSerially` are split off first and run in order ([L4925-L4940](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L4925-L4940)). Within a step, assertions run with `forEachOfLimit(asserts, PROMPTFOO_ASSERTIONS_MAX_CONCURRENCY)` (`src/assertions/index.ts` [L823-L889](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/assertions/index.ts#L823-L889)). Concurrency is forced to 1 globally by `_conversation`, `storeOutputAs`, or a persistent browser session ([L2986-L3019](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2986-L3019)).
- **Rate limits and retries.** Provider calls go through `rateLimitRegistry.execute(activeProvider, …)` (`src/scheduler/`). `DEFAULT_RETRY_POLICY` is 3 retries with exponential backoff from 1s up to 60s and 20% jitter, and it honors `Retry-After` (`src/scheduler/retryPolicy.ts` L10-L40). Hard quota errors are not retried. `AdaptiveConcurrency` (`src/scheduler/adaptiveConcurrency.ts` L29) is AIMD-like: it backs off on a 429 and recovers after sustained successes.
- **Timeouts.** A per-step timeout (`timeoutMs` / `PROMPTFOO_EVAL_TIMEOUT_MS`) is a `Promise.race` plus an `AbortController` that writes an ERROR row (`processEvalStepWithTimeout`, [L3717-L3781](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L3717-L3781)). A global `maxEvalTimeMs` stops the run and fills in timeout rows for unfinished steps (`addMaxDurationTimeoutResults`, L4630).
- **Failure handling.** A provider `response.error` becomes an ERROR row and grading is skipped (`applyRunEvalResponseOutcome`, [L1343-L1348](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L1343-L1348)). A thrown provider exception becomes an ERROR row (L1800-L1832). A thrown grading exception becomes ERROR with score 0 (`applyGradingError`, [L628-L658](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L628-L658)). Every failure lands in a row, and the run continues. `PROMPTFOO_SHORT_CIRCUIT_TEST_FAILURES` throws on the first assertion failure (`assertionsResult.ts` L316).
- **Resume and retry.** `filterCompletedResumeSteps` ([L2961-L2983](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2961-L2983)) skips `(testIdx, promptIdx)` pairs already in the DB. In retry mode it re-runs only the ERROR rows (`src/commands/retry.ts`, `src/node/retry.ts`).
- **Caching.** The cache is Keyv on disk, keyed by request, with a **14-day TTL** by default (`src/cache.ts` L38-L51). `fetchWithCache` coalesces identical in-flight requests and does not cache JSON responses that have an `error` key (L780-L960). **Repeat isolation:** `runEval` wraps each step in `withCacheNamespace('repeat:N')` when repeat > 1 (`getRepeatCacheNamespace`, [L458-L466](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L458-L466); [L1603-L1608](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L1603-L1608)), so repeat N reuses repeat N's earlier cache entries but never repeat 0's. Judge calls go through the same provider and cache path, which makes judge verdicts sticky across runs until the TTL expires.
- **Repeat.** `--repeat N` and per-test `options.repeat` emit N independent rows with *distinct* `testIdx` values ([L2662-L2689](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/evaluator.ts#L2662-L2689)). No aggregate (mean, variance, pass@k) is computed across repeats, and the stored row has no `repeat_index` column.

## Data model & storage
SQLite through Drizzle (`src/database/tables.ts`), with 26 migrations in `drizzle/`.
- `evals` ([L58-L77](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/database/tables.ts#L58-L77)) stores `id, created_at, author, description, results JSON (summary; legacy v2 table), config JSON (full resolved config), prompts JSON (with metrics), vars, runtime_options, is_redteam`.
- `eval_results` ([L79-L153](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/database/tables.ts#L79-L153)) holds one row per cell: `eval_id, prompt_idx, test_idx, test_case JSON, prompt JSON, prompt_id, provider JSON, latency_ms, cost, response JSON, error, failure_reason, success, score, grading_result JSON, named_scores JSON, metadata JSON`. It has many `json_extract` expression indexes over vars, metadata, named scores and grader reason.
- `prompts` (content-hash ID via `hashPrompt`), `datasets` (ID = `sha256(JSON.stringify(config.tests))`, `src/models/eval.ts` L492), `tags`, and the join tables `evals_to_prompts`, `evals_to_datasets`, `evals_to_tags`.
- `traces` / `spans` ([L396-L430](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/database/tables.ts#L396-L430)) are keyed by `evaluation_id`, `test_case_id` and `trace_id`, with spans stored as `{span_id, parent_span_id, name, start/end, attributes JSON, status}`. `blob_assets` / `blob_references` provide content-addressed media storage.
- Versioning is implicit. Datasets and prompts are deduplicated by content hash, and each eval snapshots its full config. There is no row-level test-case ID, so comparing two evals joins on `test_idx`.

**Comparison view.** `GET /api/eval/:id/table?comparisonEvalIds=…` (`src/server/routes/eval.ts` [L387-L421](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/server/routes/eval.ts#L387-L421)) fetches each comparison eval's page with `testIndices: indices` from the base eval, then `mergeComparisonTables` adds their columns next to the base columns. **Alignment is purely by `testIdx` position.** Reordering tests or changing `repeat` or array vars misaligns the rows. There is no statistical diff (no paired test, no confidence interval).

**CLI exit codes** (`src/node/doEval.ts` [L1269-L1284](https://github.com/promptfoo/promptfoo/blob/f74b2f44757ea073578ea3fa7bb41f9a5ef70251/src/node/doEval.ts#L1269-L1284)):
- If `passRate = successes/(successes+failures+errors)` is below `PROMPTFOO_PASS_RATE_THRESHOLD` (default 100%), the exit code is `PROMPTFOO_FAILED_TEST_EXIT_CODE` (default **100**).
- Config and option errors exit with 1 (`EvalRunError`, L144-L152). A removed option exits with 2 (`src/commands/eval.ts` L221).

The gate is an **absolute pass rate within a single run, not a regression against a baseline**. Errors count against the pass rate.

## Judge implementation
Prompts are JSON-encoded chat arrays in `src/prompts/grading.ts` (`DEFAULT_GRADING_PROMPT`, `SELECT_BEST_PROMPT`, `TRAJECTORY_GOAL_SUCCESS_PROMPT`, closedqa, factuality) and can be overridden per assertion with `rubricPrompt`. The judge provider is resolved from `assertion.provider`, then `options.provider`, then `getDefaultProviders()`, which picks based on available API keys. Output parsing takes the first JSON object and lenient-coerces its fields (`rubric.ts` L773-L918). A parse or transport failure becomes `graderFail` (score 0, flagged `graderError`). There is no calibration, no judge-agreement tracking, no multiple samples or majority vote, and no position randomization for select-best. Humans can override results in the UI with the `human` assertion type and comments.

## Online / production path
None. `tracing.otlp` starts a local OTLP receiver only to capture the SUT's spans during an eval (`TestSuiteSchema.tracing`).

## Extension model
- Custom assertions: `javascript` / `python` / `ruby` (inline or `file://`) returning `bool | number | GradingResult`, plus `webhook`.
- Custom aggregation: `assertScoringFunction`.
- Custom providers: `file://provider.js|py`, `http`, `websocket`, `exec`, MCP, and agent SDK providers (`claude-agent-sdk.ts`, `opencode-sdk.ts`, `openai/codex*`).
- Lifecycle hooks: `extensions: ["file://x.py:fn"]`, run at beforeAll, beforeEach, afterEach and afterAll.
- Derived metrics: mathjs expressions over named scores.
- Built-in assertion types themselves are a closed enum.

## Strengths
- A clean pass/fail/error split in `ResultFailureReason` that is persisted per row and indexed. Resume and retry operate on it (`types/index.ts` L380; `tables.ts` L104, L121).
- Hierarchical weighted scoring (assertion → assert-set → test) with named metrics and a thoroughly edge-cased threshold override (`assertionsResult.ts` L261-L422).
- Trajectory assertions work on normalized OTel spans rather than the model's text. They are framework-agnostic across OpenAI, Anthropic, Gemini, Vercel AI SDK and Codex attribute conventions, with glob matchers, partial/exact args, ignore and defaults (`trajectory.ts`, `toolAttributes.ts`).
- `tool-call-f1` normalizes tool calls across vendors and has a linear-time, bounded parser for messy text (`toolCallF1.ts` L20-L201, L216-L347).
- The `graderError` flag keeps inverted judge assertions from turning infrastructure errors into passes (`matchers/shared.ts` L47-L61).
- Operationally solid execution: adaptive concurrency, Retry-After-aware backoff, per-step and global timeouts, in-flight request coalescing, and repeat-scoped caching (`scheduler/`, `cache.ts`, `evaluator.ts` L3717, L458).

## Weaknesses
- Multi-turn is split into three unrelated mechanisms. `_conversation` makes each test a turn and serializes the whole eval ([#385](https://github.com/promptfoo/promptfoo/issues/385), open since 2024-01). The simulated user flattens the conversation into one string and needs promptfoo's hosted model (`providers/promptfoo.ts` L331-L367). Its `userProvider` option is dead code (`simulatedUser.ts` L38). There is no per-turn grading outside red-team providers.
- Tool-call validity is tied to OpenAI's format and to the SUT's provider config (`assertions/openai.ts` L43-L69). `tool-call-f1` ignores arguments and order. Trajectory assertions depend on the SUT emitting correctly-attributed OTel spans ([#10518](https://github.com/promptfoo/promptfoo/issues/10518)) and cannot yet check tool success ([#10607](https://github.com/promptfoo/promptfoo/issues/10607)).
- Rows are identified by position (`testIdx`), and comparison joins on it (`server/routes/eval.ts` L395-L402). Repeats get separate `testIdx` values with no aggregation (`evaluator.ts` L2668-L2689).
- The CI gate is an absolute pass rate that counts errors as failures, with no baseline or significance test (`doEval.ts` L1269-L1284).
- Judge parsing is lenient: a missing `pass` defaults to true (`rubric.ts` L901). Select-best takes the first integer found and has no position-bias control (`comparison.ts`). G-Eval omits the paper's logprob weighting. Judge results are cached for 14 days by default, so re-running does not re-sample the judge.
- Core agentic red-team attackers (GOAT, simulated-user) call a closed remote service (`goat.ts` L407-L437), and turn caps depend on cloud login (`crescendo/index.ts` L209-L212).

## Worth adapting
- **Tri-state row outcome (pass / assert-fail / error) persisted and indexed.** This lets regression gates and retries treat infrastructure errors separately from quality failures.
- **Weighted assertion sets with a threshold override and `weight: 0` metric-only checks.** This expresses "must-pass" and "soft score" checks in one model.
- **Trajectory assertions over a normalized step list extracted from OTel spans**, with attribute-family tables per framework. This decouples tool-use checks from each SDK's response shape, and the matchers (glob, in-order subsequence, partial args plus ignore and defaults) cover most tool-use assertions.
- **Cross-vendor tool-call extraction** (OpenAI, Responses, Anthropic, Gemini) for name-level metrics like tool-call F1.
- **A `graderError` marker** so judge failures are neither silently inverted nor confused with quality failures.
- **Repeat-scoped cache namespaces**, so repeated trials are real re-samples while still being cacheable individually.
- **Wrapping the SUT with a "driver provider"** (simulated user, attacker) that receives `originalProvider`. It composes cleanly with any target, provided the driver returns structured turns and not a flattened string.

## Don't copy
- **Position-based row identity (`testIdx`) for comparisons and resume.** Adding, reordering or expanding tests silently misaligns cross-run diffs. Use stable content or user-assigned test IDs.
- **Conversation state as a global mutable var keyed by test order**, which forces concurrency to 1. Model a conversation as one test case with ordered turns, and parallelize across conversations.
- **Flattening a multi-turn transcript to a single `output` string** for grading. Per-turn and tool-level assertions become impossible without re-parsing.
- **A closed enum plus a static handler map for assertion types.** Every new scorer is a core edit, and third-party scorers end up in script escape hatches.
- **Lenient judge parsing** (default pass=true, the first integer anywhere wins). It hides judge malfunctions as passes or wrong picks. Validate strictly and surface parse failures as errors.
- **A long-TTL response cache applied to judges by default.** It makes judge variance invisible across runs.
- **An absolute pass-rate exit code as the only CI signal.** It has no notion of a baseline or of noise.
- **Hard dependency on a vendor-hosted model for core simulation features.**
